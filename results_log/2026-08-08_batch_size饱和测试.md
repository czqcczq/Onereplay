# Batch size 饱和测试（2026-08-08，Job 2831163）

## 结论

micro-batch=8 时 **GPU 已经吃满吞吐**。相同样本量下 batch 从 8 加到 16，总时间比是 **1.015**（几乎相等），`tokens/s` 反而从 10181 掉到 10026。加大 micro-batch 换不到速度，只换显存（21.29 → 39.28 GiB）。

由此定下 replay 的混合方案：**用 `4+4` + accumulation ×2，不用 `8+8`**。

配置：Qwen3-1.7B + LoRA (r=8, α=16, q_proj/v_proj)，Commonsense170k，H100 80GB HBM3 单卡，`max_len=512`，动态 padding，seed=1，纯 vanilla（`--replay_lambda 0 --measure_replay_when_lambda_zero 0`）。

## 为什么要做

老师提的问题：batch 很小时可能没把 GPU 用满，那么 batch×2 消耗的时间不一定翻倍——按道理时间该乘 2。如果基线 batch 处在欠载区，测出的「replay 只贵 X%」就会被低估，因为那份便宜来自基线浪费掉的算力，不是方法本身高效。

这个问题直接决定 replay 的两种混合方案谁更优，所以必须先测。

## 实验设计：为什么用「样本数对齐」而不是「步数对齐」

按步数对齐（两档都跑 400 步）有个麻烦：两档每步的真实 token 数不是严格 2 倍（动态 padding 导致 919.8 vs 1816.9，比值 1.975），判据得额外做修正。

改成**固定样本量**：让每档都吃掉 6400 个样本，b8 跑 800 步、b16 跑 400 步。于是两档吃的是同一批样本、同样多 token（726741，实测四个 run 完全一致）、同样 100 次优化器更新，判据就变成一句话：

- **两档总时间接近** → 时间正比于计算量 → b8 已饱和
- **b8 总时间明显更长** → 小 batch 留了算力闲置 → b8 欠载

另外三个针对上一版教训的设计：开头一个丢弃的 warmup run 把 GPU 时钟和 page cache 拉起来；ABBA 顺序（rep1 跑 8→16，rep2 跑 16→8）让位置效应对两档对称；`--exclusive` 独占节点。

## 结果

### 逐次观测

| batch | rep | steps | samples | tokens | train (s) | ms/step | tokens/s | peak alloc (GiB) |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 8 | 1 | 800 | 6400 | 726741 | 72.23 | 90.3 | 10061 | 21.29 |
| 8 | 2 | 800 | 6400 | 726741 | **71.39** | 89.2 | 10181 | 21.29 |
| 16 | 1 | 400 | 6400 | 726741 | **72.49** | 181.2 | 10026 | 39.28 |
| 16 | 2 | 400 | 6400 | 726741 | 72.50 | 181.2 | 10025 | 39.28 |

重复之间取**最快**的一次作为代表：外部干扰只会让 run 变慢不会变快，所以最小值是对真实开销的最好估计。

### 判据

| batch | steps | 最快 train (s) | vs b8 总时间 | 单步倍数 | ms/step | tokens/s | peak alloc (GiB) |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 8 | 800 | 71.39 | 基准 | 基准 | 89.2 | 10181 | 21.29 |
| 16 | 400 | 72.49 | **1.015** | 2.03x | 181.2 | 10026 | 39.28 |

三个互相印证的读数：

1. **总时间比 1.015**。相同计算量下两档几乎同时完成，b8 没有可被更大 batch 利用的闲置算力。
2. **单步倍数 2.03**，而每步 token 比精确是 2.000。时间涨得比计算量还多 1.5%，多出来的是 padding 浪费——batch 越大，越容易被一条超长序列拖着让其他样本陪着补 pad。
3. **`tokens/s` 反向**：b8 的 10181 比 b16 的 10026 高 1.55%，与上一条同源。

机制上的解释：Transformer 里除 attention 内部之外的所有线性层，都把 `[batch, seq, hidden]` 压平成 `[batch × seq, hidden]` 再做矩阵乘。所以 batch=8 时 GEMM 看到的 M 维度不是 8，而是**每步的 token 数约 908**。配上 hidden=2048、intermediate=6144，这个规模切出的 tile 已经能把 H100 的 132 个 SM 铺满好几轮，再加 batch 只是增加轮数。饱和点取决于**每步 token 数**，不是样本数。

## 对 replay 混合方案的决定

两种方案都保证每次更新的 new task 样本数不变：

| 方案 | 总时间 | 峰值显存 | 与饱和度的关系 |
|---|---:|---:|---|
| `4+4` + accum ×2 | **×2.00** | **21.29 GiB** | 无关（单步不变、步数翻倍） |
| `8+8` | ×2.03 | 39.28 GiB | 取决于饱和度 |

**选 `4+4`。** 它在两个维度都不差：时间上略优，显存少花 18 GiB。理由比「省显存」更强——既然已饱和，`8+8` 多付的那份单步耗时里没有任何并行收益可以抵扣。

`4+4` 的成本恒为 ×2.00 且与饱和无关；`8+8` 的成本则完全由饱和程度决定。若当初测出的是欠载（比如时间比 0.66），`8+8` 只需 ×1.32 就会反超。所以这个判据是必须先做的，不是可选的验证。

## 显存：严格线性，b32 是硬上限

| batch | peak allocated (GiB) |
|---:|---:|
| 8 | 21.29 |
| 16 | 39.28 |
| 32 | 75.27（Job 2815257） |
| 64 | 预测 147，实测 OOM |

拟合 `峰值 ≈ 3.3 + 2.25 × batch`，截距对应 Qwen3-1.7B 的 bf16 权重，斜率是每单位 batch 的激活。

- **b64 在数学上不可能**：需要约 147 GiB，是卡容量 79.18 GiB 的 1.86 倍。Job 2815257 里它在分配到 77.89 GiB 后再要 11.59 GiB 时 OOM，连一步都没跑完。
- **b32 虽能跑但不安全**：reserved 77.62 / 79.18 = 98%，只剩 1.5 GiB 余量，任何序列长度波动都会 OOM，不适合正式实验。
- 安全区是 **b16**（reserved 42.68，占 54%）。而 b8 已饱和，所以生产配置用 b8 即可，剩下 73% 的显存买不到速度。

## 正则绝对开销：四次独立测量都落在 9–11 ms/step

饱和结论要能套到成本报告上，前提是正则的开销与 batch 无关。四次独立测量支持这一点：

| 场景 | 无正则 | 有正则 | 绝对开销 | 相对开销 |
|---|---:|---:|---:|---:|
| SFT b8（21090 步稳态，Job 2649412） | 88.0 ms | 97 ms | 9.0 ms | +10.2% |
| SFT b8（profile 分解，Job 2649412） | 93.0 ms | 103.2 ms | 10.2 ms | +11.0% |
| SFT b32（稳态区间，Job 2815257） | 366.9 ms | 375.4 ms | 8.5 ms | +2.3% |
| OPD b4（稳态区间，Job 2832597 vs 2649408） | 198.3 ms | 208.9 ms | 10.6 ms | +5.3% |

（相对开销一律以「无正则」为分母，即正则让训练变慢的比例。）

batch 跨 4 倍（8→32）、paradigm 跨 SFT/OPD，绝对开销都是 9–11 ms。原因在代码上是显然的：正则算的是 `tr(ΔW C ΔWᵀ)`，只读 LoRA 的 A/B 权重和 C 矩阵，batch 里有几条样本、序列多长都不进这个式子。

profile 数据还给出了这 10 ms 的去向：前向算正则 4.2 ms，反向对 A/B 求这一项的梯度 5.5 ms。都是真实 GPU 计算，且与 task_loss 的 kernel 在同一个 CUDA stream 上串行执行——即使 GPU 有空闲 SM 也不会被「吸收」，所以是加性的。这也解释了为什么 b8（更接近欠载）测出的开销没有比 b32 更小。

推论：**相对开销 = 9~10 ms ÷ 单步时间**，随 batch 反比衰减。所以报相对百分比时必须写清 batch。

## 数据质量：这次为什么可信

- **重复性**：b16 两次是 72.487 s 和 72.495 s，差 **0.008 秒**（0.01%）。
- **样本对齐自检通过**：四个 run 的 `train_tokens` 全是 726741。
- **确定性复现**：同 batch 不同 rep 的 loss 逐位相同（b8 两次 step 100 都是 1.381724；b16 两次 step 50 都是 1.603673）。
- **warmup 生效**：warmup run 前 25 步是 189.8 ms，而正式 run 的第一个窗口（1–100 步）已经是 94.2 ms，基本直接进入稳态。
- **与历史交叉验证**：b8 的 `win` 序列稳定在 85–94 ms、`sec_per_step` 89.2 ms，与 Job 2649412 全量 21090 步反推的稳态 88.0 ms 吻合。

## 上一版（Job 2815257）为什么废掉

记在这里以免重犯。那次 `15_bench_batch_scale.slurm` 扫 8/16/32/64，结果只有 b32 一档可用：

- **b8 档物理上自相矛盾**：区间速度 325 → 177 → 152 → 146.5 ms，跑完 400 步还在下降；且 OneReplay 稳态 113.6 ms 反而比 vanilla 稳态 146.5 ms 快 22%，这不可能发生。根因是 b8 vanilla 是整个 job 的第一个 run，独自承担了 CUDA context 创建、cuDNN autotune、数据集首次读盘，而 400 步 × 8 样本这个分母摊不掉。
- **b16 档被外部干扰**：OneReplay 稳态约 425 ms vs vanilla 193 ms（+120%），远超正则应有的 +4.5%，且区间序列 497 → 427 → **435** → 410 出现反弹，典型的被同节点任务抢占。
- **b64 必然 OOM**，而且 `set -euo pipefail` 让它掐死了整个 job，后面的 run 全没跑。
- **b32 反而干净**：单步 369 ms 时，每步几毫秒的 CPU 调度和数据加载只占 1–2%，被完全淹没；b8 单步只有 88 ms，同样的固定开销占 10% 以上。

本次的对应修正：加 warmup run、加 `--exclusive`、改成按样本数对齐、ABBA 顺序、给 `bench_run` 加 `|| true`、以及在 `trainers/base.py` 的日志里增加 `win=` 区间速度字段（累计平均会一直把冷启动摊到最后，短跑上永远看不到稳态）。

## 由此确认 / 修正的旧结论

- 上一版那个 b8 = 146.5 ms **确认是污染值**，真值是 89 ms 左右。
- 上一版同 job 的 b8 vs b16 给出总时间比 0.658（指向「严重欠载」）**是假信号**，真值 1.015。
- 跨 job 拼接得到的 88.0 ms 稳态**是对的**。
- 上一版的 b16 也带轻微污染：那次反推 192.8 ms，本次独占环境下是 181.2 ms，快 6%。因此早先据此预测的单步倍数 2.19 偏高，真值 2.03。

## 复现

```bash
sbatch onereplay/slurm/16_bench_saturation.slurm
# 加 b32（有 OOM 风险，已用 || true 保护）
BATCHES="8 16 32" sbatch onereplay/slurm/16_bench_saturation.slurm
# 更多重复压噪声
REPEATS=4 sbatch onereplay/slurm/16_bench_saturation.slurm
```

汇总（job 末尾会自动跑一次）：

```bash
python -m onereplay.scripts.summarize_saturation \
  --metrics_dir <RESULTS_ROOT>/metrics/cost/saturation
```
